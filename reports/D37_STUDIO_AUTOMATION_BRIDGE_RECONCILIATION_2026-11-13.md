# D37-A — Studio Automation Bridge Reconciliation Matrix

**Date:** 2026-11-13  
**Scope:** Read-only reconciliation of WP2/WP3/WP4/WP5/WP6 contracts, owner decisions, and the existing local autonomy specialists/task/artifact implementations.  
**Disposition:** No adapter, schema, API, or code implementation authorized by this report.

## Executive finding

The repository contains a usable **local prototype path** for research collection, research-dependent short-script drafting, and procedural short generation in dry-run mode. It does not contain a canonical Studio bridge. The local runtime uses `nextdecode.autonomy.*` schemas, generated local IDs, local task/plan records, and JSON artifacts under `outputs/autonomy/artifacts`; the WP2–WP6 register requires canonical ownership, typed cross-domain identity, and owner-approved reconciliation before those records can be projected or renamed as WP records.

The safe current disposition is therefore: **reuse the local specialists behind a future bounded adapter, but do not map local identities or fields into canonical WP2–WP6 contracts yet.**

## Status vocabulary used here

- **Accepted baseline:** direction already established by accepted decisions or the traceability register.
- **Working reconciliation:** current cross-package boundary, explicitly not a freeze.
- **Open owner decision:** the source names an unresolved owner/security/policy choice.
- **Local prototype:** code that exists and is executable in the repository, without canonical integration proof.
- **Canonical target:** the contract boundary the code would eventually have to satisfy.
- **Mapping rule:** a conservative rule for a future adapter; it is not a proposed schema field or invented ID.
- **Implementation blocker:** evidence that prevents safe canonical integration now.

## Owner-decision docket before any bridge implementation

1. Freeze the WP1/WP2 logical-versus-physical Job/Attempt ownership and field boundary.
2. Resolve WP2/WP3 lease, heartbeat, fencing and revocation responsibilities.
3. Approve the WP4 artifact registration/version/provenance mapping, including retention and deletion behavior.
4. Approve the WP5 policy interface and protected-action catalogue; retain centralized, fail-closed authorization.
5. Approve the Part 7 Studio adapter contract or a superseding canonical contract; Part 7 alone is not authorization.
6. Approve the isolated WP6 environment, Artifact 07 crosswalk, test parameters and execution authorization.

## Bottom line

The smallest safe future bridge is an adapter that submits an owner-approved canonical execution request, invokes the existing local specialist/Studio implementation as a bounded worker operation, registers output through the canonical WP4 boundary, and asks WP5 for any protected-action decision before side effects. That is a **canonical target**, not an implementation performed here. Until the docket above is resolved, the local autonomy path should remain visibly labeled as local prototype/runtime data.
